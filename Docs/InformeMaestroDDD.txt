Informe maestro de estrategia - DelegIA / Clínica Dental Vitalis

1. Objetivo del proyecto

La estrategia correcta no es construir simplemente un CRUD de leads, sino construir un mini CRM comercial interno, orientado a seguimiento y con IA integrada, que resuelva el problema de negocio descrito por Vitalis:

centralizar leads, evitar pérdida de seguimientos, reducir duplicados y acelerar el contacto con leads de alto valor.

Esto encaja especialmente bien con el posicionamiento actual de DelegIA: la empresa presenta su propuesta alrededor de sistemas internos personalizados, CRM y seguimiento comercial con IA, automatización, trazabilidad y supervisión humana. En su web describen precisamente la unificación de leads procedentes de diferentes canales, el seguimiento del pipeline y la intervención humana donde aporta criterio. 

La prueba confirma que no buscan una maqueta: exigen una aplicación funcional, desplegada, conectada a una base de datos real, autenticada y con una integración real de OpenAI/Claude. DelegIA_Prueba_Tecnica_weasy2_1.pdf

Por tanto, la candidatura debe transmitir cuatro capacidades:

producto + ingeniería + IA aplicada + criterio operativo.

18. ¿Puede cambiar la clínica?

Sí.

Esta es una decisión que dejaría explícita en README.

Motivo:

un lead puede haber llegado inicialmente a Madrid pero posteriormente indicar que Valencia le resulta más conveniente.

Bloquear la clínica original produciría datos operativos incorrectos.

Pero distinguiremos:

original_clinic_id
clinic_id

Así mantenemos:

Origen:
Madrid
Clínica actual:
Valencia

Esto permite en el futuro analizar:

¿Qué clínica recibe más leads?
¿Qué clínica termina atendiendo más?
¿Cuántos leads se reasignan?

Es una decisión mucho más sólida que simplemente sobrescribir el campo.

⸻

19. ¿Qué hacer con teléfonos duplicados?

No fusionaría automáticamente.

Decisión:

detectar + avisar + permitir decidir.

Cuando se crea un lead:

Existe un lead con este teléfono.
Madrid
Implantes
Contactado
Creado hace 2 días
[Ver lead existente]
[Crear de todos modos]

Si se crea de todos modos:

duplicate_of = <lead original>

¿Por qué?

Porque fusionar automáticamente puede eliminar información válida:

lead A → implantes
lead B → ortodoncia

o:

lead A → Madrid
lead B → Valencia

Además, el sistema conserva la trazabilidad original.

25. Borrado de leads

El PDF exige poder eliminar leads. DelegIA_Prueba_Tecnica_weasy2_1.pdf

Pero dado que queremos trazabilidad, recomiendo:

Soft delete

Añadir:

deleted_by

y no eliminar físicamente el registro.

Desde la interfaz:

Eliminar lead

produce:

y desaparece del listado normal.

La auditoría conserva:

Esto es más apropiado para un CRM real.

29. Modelo IA

La elección para el MVP será:

gpt-5.6-luna

manteniendo el modelo configurable mediante:

OPENAI_MODEL=gpt-5.6-luna

La documentación actual de OpenAI presenta GPT-5.6 Luna específicamente como modelo optimizado para cargas de trabajo sensibles al coste, con:

Input:  $0.20 / 1M tokens
Output: $1.20 / 1M tokens

y soporte para Responses API. 

Para este caso es una elección excelente porque generar un WhatsApp personalizado necesita muy poco contexto y poca salida.

⸻

30. Estimación de coste IA

Supongamos por ejemplo:

1000 tokens entrada
300 tokens salida

Coste aproximado:

1000 × $0.20 / 1M = $0.00020
300 × $1.20 / 1M = $0.00036
--------------------------------
≈ $0.00056 / generación

Incluso:

10.000 generaciones
≈ $5.60

Esto hace innecesario utilizar un modelo inferior sólo por coste.

31. Prompt

El prompt debe estar versionado en código.

Por ejemplo:

SYSTEM_PROMPT_VERSION=1.0

Rol:

asistente de seguimiento comercial para una clínica dental.

Reglas:

- Escribe en español.
- Tono cercano y profesional.
- Ser breve.
- No hacer diagnósticos.
- No proporcionar recomendaciones médicas.
- No inventar descuentos.
- No inventar disponibilidad.
- No afirmar que una cita está reservada.
- No utilizar información que no esté presente.
- Adaptar el mensaje al estado del lead.
- Adaptar el mensaje al tratamiento.
- El mensaje debe sonar humano.
- Debe ser adecuado para WhatsApp.

36. Privacidad

Aquí hay una cuestión especialmente importante.

Aunque el ejercicio utiliza un cliente ficticio, un CRM de una clínica dental podría tratar información relacionada con salud. La AEPD considera los datos relativos a la salud una categoría especialmente protegida y el artículo 9 RGPD establece restricciones específicas sobre su tratamiento. 

Por ello diseñaremos el MVP siguiendo minimización de datos:

No almacenar:

* historia clínica;
* diagnósticos;
* radiografías;
* enfermedades;
* medicación;
* información clínica no necesaria.

Sólo:

nombre
teléfono
clínica
tratamiento de interés
fuente
estado
seguimiento comercial

Y las notas deberán ser de naturaleza comercial/operativa.

En el README dejaría claro que una versión productiva requeriría revisión jurídica, política de conservación, base legitimadora, encargados de tratamiento y medidas de seguridad adecuadas.
